## Architecture (for the reviewer)

- `engine/`: the whole solver (model types, validation, RCM, skyline LDL^T, post-processing, generator, sweep). No dependencies.
- `bridge/session/`: handle-based flat-buffer API shared by both bridges (geometry, results and stats are `[]float64`).
- `bridge/native/`: Go `c-shared` exports (`f2d_*`) for dart:ffi. Bindings are generated by ffigen into `app/lib/generated/`.
- `bridge/wasm/`: Go `js/wasm` exposing a global `f2dEngine` object, called from Dart through `dart:js_interop`.
- `cmd/frame2d` (CLI), `cmd/server` (net/http + SQLite via `modernc.org/sqlite`, pure Go).
- `app/`: Flutter UI (desktop + web). Dart holds state and draws; every number comes from the Go engine.
- Result buffers: desktop gets zero-copy `Float64List` views over pinned Go memory (`runtime.Pinner`); web gets a memcpy into a fresh `Float64Array` per call.

## Toolchain surprises / problems over ~10 minutes

### ffigen needs an x64 libclang on win-arm64
- Time lost: ~15
- Category: build_config
- What happened: Dart/Flutter run as x64 under emulation on this machine, but the installed LLVM (`C:\Program Files\LLVM`) is ARM64, so ffigen died with "%1 is not a valid Win32 application" loading `libclang.dll`.
- What fixed it: `stack.sh` (`_ensure_libclang`) downloads the `libclang` PyPI wheel for `win_amd64` and unpacks its `libclang.dll` into `.tools/llvm-x64/{bin,lib}` (git-ignored); `app/ffigen.yaml` points `llvm-path` at it. Bindings are regenerated only when the exported C header changes.

### Go c-shared on Windows needs an x64 C compiler
- Time lost: ~5
- Category: build_config
- What happened: the Flutter Windows runner is x64 here, so the Go library must be `windows/amd64`, but the host is arm64 and has no gcc/mingw.
- What fixed it: `CC="zig cc -target x86_64-windows-gnu"` (Zig 0.17.0 is already pinned for the run). Pure-Go outputs (CLI, server, js/wasm) stay native arm64 and CGO-free. Consequence: the desktop engine runs under x64 emulation, so the 50x50 solve in the app is slower than the arm64 CLI.

### cgo "result is unpinned Go pointer" panic
- Time lost: ~10
- Category: ffi
- What happened: `f2d_stats` returned a pointer into the `Session` struct; because the struct contains Go pointers, cgocheck rejected it even though the field was pinned.
- What fixed it: result buffers must be pointer-free allocations of their own (`new([7]float64)`, `make([]float64, n)`) pinned with `runtime.Pinner`. Same rule for the error string and serialized model.

### drawRawPoints is extremely slow on Impeller (GLES) for many segments
- Time lost: ~20
- Category: wrong_result (performance)
- What happened: the 50x50 drag frame was ~165 ms with `raster_p50` = 163 ms and `paint_p50` = 1 ms (35k line segments via `Canvas.drawRawPoints(PointMode.lines)`).
- What fixed it: build one `Path` per colour bin (`moveTo/lineTo` pairs) and `drawPath` it. Raster dropped to ~4 ms; drag frame p50 ~33 ms (now dominated by the emulated-x64 Go solve).

## Deviations (Emscripten, UI fallback, extra dependency, spec question)

- No Emscripten. Web engine is Go `js/wasm` (`GOOS=js GOARCH=wasm`), `wasm_exec.js` copied from `$GOROOT/lib/wasm` into the web output by `build_web_release`.
- Extra dependencies beyond the Flutter SDK: `ffi` (calloc/Utf8 for dart:ffi), `web` (package:web for file open/save on web), dev: `ffigen`. Go: `modernc.org/sqlite` (pure-Go SQLite driver) and its transitive modules.
- Desktop "Open"/"Save" ask for a file path in a dialog (no file-picker plugin, to keep the Windows build free of native plugins). Web uses a real file input / download.
- The solve runs synchronously on the UI thread in both desktop and web, so `lag_frames` is always 0 (SPEC 5.5 allows UI-thread solving but asks for the field).
- `frame_ms` in the drag/render bench = wall time from the start of an iteration (input + solve) to the post-frame callback, i.e. it includes the vsync wait. The BENCH line carries extra diagnostic fields: `paint_p50` (Dart paint recording), `build_p50`, `raster_p50` (Flutter `FrameTiming`).
- `peak_heap_bytes` (CLI) is sampled every 2 ms via `ReadMemStats`, approximate by spec. The measured region includes `Prepare` (RCM, numbering, skyline allocation) as well as the solve.
- `stack.sh` `build_web_release` builds `--wasm` by default; `F2D_WEB_MODE=default` builds the default (dart2js/CanvasKit) build into the same `app/build/web` directory.
- Spec question (no action needed): "equilibrium_residual" is not defined precisely; it is computed as |sum of forces| / max(1, sum of |load| and |reaction| magnitudes) over Fx and Fy only (moments are not included).
- Spec question: the RCM pseudo-peripheral loop keeps the previous root when the new candidate does not increase eccentricity; with this reading `gen 10 10` gives profile 10221 -> 7575 and the 50x50 golden matches exactly.

## Profile of the Go solver (before)

`frame2d bench 100 100` under pprof (CPU samples, 2.3 s): `engine.dot` 66% flat (inlined skyline inner product), `factor` 71% cumulative, `solveInPlace` 7%, runtime/GC/preempt (the heap-sampler goroutine) about 15%, assembly under 1%. Allocation: 55,742 mallocs / 73 MB for 100x100. Factorization is the hot path. The Zig port keeps the algorithm (SPEC 4.4) and changes only: a 4-wide `@Vector` dot product (Go has no vectorized reduction), an arena per model (17 allocations instead of about 55k), a preallocated solve workspace, and flat CSR adjacency for RCM. The profile file is kept at `build/baseline/cpu.prof` (git-ignored).

## What was built

- `zig/src/` engine in Zig 0.17.0, std only: `json.zig` (DOM parser), `model.zig` (types, JSON in/out, generator, error codes), `engine.zig` (prepare, RCM, skyline LDL^T, post-processing; `pivot_tol` carries `BENCH-EDIT:leaf`, `Node.bench_pad` carries `BENCH-EDIT:struct`), `results.zig` (results JSON, sweep), `session.zig` (flat-buffer session for Flutter, same layout as before), `lib.zig` (C ABI, header `zig/include/frame2d_engine.h`), `tests.zig` (6 unit tests via `zig test`).
- One source, three artifacts built by `stack.sh`: `build/libframe2d.a` (static, host arch, linked into the Go CLI/server through cgo with `CC="zig cc -target <host>"`), `build/frame2d_engine.dll` (x86_64 shared lib for dart:ffi, same `f2d_*` ABI as the old Go c-shared lib, so the Dart code and ffigen flow are unchanged), `build/engine.wasm` (wasm32-freestanding, no Emscripten, loaded by the hand-written `app/web/f2d_loader.js`, which exposes the same `f2dEngine` object the Dart web engine already used).
- Go is now HTTP + SQLite (`cmd/server`), CLI argument handling (`cmd/frame2d`) and `bridge/zig` (cgo wrapper that only moves bytes; sweep concurrency is goroutines that each own a Zig-side forked model). The Go `engine/`, `bridge/session`, `bridge/native`, `bridge/wasm` packages and `wasm_exec.js` are deleted: no Go engine remains in the client. The server binary has a `bench-boundary` subcommand (Go to Zig through cgo).
- `stack.sh`: Zig caches are stack-local (`.zig-global`, `.zig-cache`), so `clean_all` never touches a global cache shared with other agents. `CC` is scoped to Go commands only (Flutter CMake would pick up a global `CC`). `go build` does not hash a library contents into the link action, so the lib md5 is passed with `-ldflags -X frame2d/bridge/zig.libStamp=...` to force a relink.
- Conformance: `harness/conformance.py go-zig-flutter all` 22/22, `harness/server_conformance.sh go-zig-flutter` all passed, `test_all` (zig tests, go test, flutter test) green, `build_check` green.

## Deviations

- No Emscripten. The static library is consumed by Go; Flutter desktop loads a shared library built from the same Zig sources (dart:ffi needs a dynamic library). Web uses `wasm32-freestanding` with one import (`env.f2d_now_ms`).
