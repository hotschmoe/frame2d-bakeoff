# Kickoff prompt: P5 optimization pass (all 7 stacks)

Not in SPEC; added after run1 on 2026-10-24 at the human's request. The run1 code is frozen as the baseline (tag `run1-baseline`). P5 gives each finished stack **one** fresh agent session to make it idiomatic and fast, then the stack is re-measured with the same lean protocol and the leaderboard is compared. Run with a fresh context per stack, one agent per stack, same prompt for every stack.

## Prompt (replace `<stack>`)

> You are doing a one-pass **optimization and best-practices review** of the finished **`<stack>`** stack of Frame2D. Read `SPEC.md` (at least §2, §4, §5, §6, §8.2-8.8, §9.1-9.3) and `CLAUDE.md`. Work only in `stacks/<stack>/`. Do not read, list or grep any other `stacks/*` directory, and do not edit `SPEC.md`, `fixtures/` or `harness/`.
>
> **Goal:** improve what the human cares about, in this order of value: (1) dev-loop build time (`build_check` / `build_dev` after a small edit, and no-op rebuilds), (2) cold build time, (3) in-app performance (desktop and web drag/render/startup, server throughput and latency, CLI solve time), (4) resources (RSS, CPU per request), (5) binary / bundle / web download size. Also fix real defects. The way to get there is idiomatic code and best-practice build configuration for this language and framework, not benchmark tricks.
>
> **Inputs (read these first):**
> - `harness/kickoff/p5-baseline/<stack>.md`: your stack's run1 numbers on this machine.
> - `results/run1/win-arm64/review/<stack>.md`: an independent code review of your stack, with reported defects. Verify each defect before fixing it.
> - `stacks/<stack>/AGENT_LOG.md`: what earlier agents ran into.
>
> **Look at, at least:**
> - `stack.sh`: does a no-op `build_check` / `build_dev` do real incremental work, or redo fixed work (regenerating bindings, re-copying, rebuilding unchanged libraries, `flutter clean`, etc.)? Make every step incremental and skip work whose inputs did not change (content- or timestamp-based, the way make/the toolchain would). Keep each function's meaning from SPEC §5.6: `build_check` still type-checks everything, `build_dev` still produces runnable dev artifacts for everything the agent normally rebuilds, and each must still pick up an edit to any source file.
> - Build configuration best practice for this toolchain: release profiles (LTO, codegen units, strip, panic strategy, `-ldflags`, `-trimpath`, `-Doptimize` mode, Flutter split-debug-info / tree-shaking, wasm-opt), and dev-profile settings that speed the edit loop (e.g. SPEC §9.3 ideas where they apply on Windows). All flags stay inside `stack.sh` or the project's own config files.
> - Hot paths: the skyline factorization and solve (§4.4), assembly, the sweep, JSON encode/decode, server request handling, the UI drag/render path, and the engine↔UI bridge. Profile before changing; don't guess.
> - Idiom and correctness: error codes and exit codes per §5, resource leaks, unchecked nulls, missing tests (especially P2 springs/releases).
>
> **Hard rules:**
> - Keep the stack's identity: same languages, same UI framework, server framework and bridge, same architecture split (engine in the systems language). The solver stays hand-written to §4.4's algorithm; no linear algebra or numeric libraries (§2.3). Do not add new dependencies other than build/test tooling, and do not upgrade the toolchain or change dependency versions.
> - Keep the `BENCH-EDIT` markers (§9.2) in place and meaningful (leaf, struct, server, ui).
> - Build and test only through `stack.sh` functions wrapped in `harness/measure.sh` (label your records `p5-...`).
> - Everything must stay green: `harness/conformance.py <stack> p1`, `harness/conformance.py <stack> p2`, (go-zig-flutter: also `p3`), `harness/server_conformance.sh <stack>`, and all bench modes (§5.5) on desktop and web.
> - To check an effect, you may run the smoke harnesses with `F2D_RUN=run1p5`: `harness/runtime/run.sh <stack> <sections> --quick` and `harness/buildloop/run.sh <stack> <sections> --quick`. Other agents are optimizing other stacks on this machine at the same time, so your timings are noisy; prefer large, explainable wins and compare against your own before-numbers taken the same way, not against the baseline file alone. The real measurement is done afterwards on a quiet machine.
> - Never kill processes by image name (no `taskkill /IM`, `pkill <name>`, `Stop-Process -Name`); other agents' processes are running. Kill only PIDs you started. Use a server port other than the default if one is busy (`FRAME2D_ADDR`).
> - Do not commit. Leave the changes in the working tree.
> - Time box: 75 minutes of wall time. Stop earlier when the remaining ideas are small.
>
> **Deliverable:** add a `## P5 optimization pass` section to `stacks/<stack>/AGENT_LOG.md` with: each change (one line: what, why, which metric it targets), smoke before/after numbers where you measured them, defects from the review you fixed or rejected (and why), ideas you didn't get to, and the final conformance results. Finish your reply with the same summary.
